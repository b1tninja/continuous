# Mid-session tool changes that cost nothing

Status: research, 2026-11-14. Docs only: no product code, no `plans/ROADMAP.md` edit, no model call, no spend. Read against `origin/main` at `56e126969` and the diff of PR #750 (draft). Provider facts were fetched on 2026-11-14 from the live pages cited inline. Anything I could not confirm from a primary page, or did not run, is marked **unverified**.

The question: adding or removing a tool mid-session rewrites the very front of the prompt (render order is tools, then system, then messages), so the whole cache is rewritten once. A separate PR (C80, C88) warns about that cost and defers the change to the next cold cache. This note asks how to make "apply now" free, by two routes:

- **Route A, provider-native.** The provider lets a request declare tools up front and change the offered set by appending to `messages`.
- **Route B, our own indirection.** A byte-stable tool list: `search_tools` lists every deferred name in a fixed order and one stable `call_tool({name, arguments})` dispatches by real name, so an activation only appends to `messages` (Track Z rows Z1, Z3, Z8, Z10, Z11).

## 1. Summary

1. **Route A is real, but only on Anthropic Messages-API endpoints, and the fork does not have one on Bedrock.** Anthropic's mid-conversation tool changes (`tool_addition` / `tool_removal` blocks in an appended `role: "system"` message) keep the cache and keep earlier thinking valid. By reference (`mid-conversation-tool-changes-2026-07-01`) they run on the Claude API, Claude Platform on AWS, both Google Cloud platforms, Microsoft Foundry and **Claude in Amazon Bedrock (the `bedrock-mantle` Messages endpoint)**; by value (`inline-tools-2026-09-15`) on the Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed) and Foundry. Not on `bedrock-runtime` (InvokeModel or Converse). The fork's Claude-on-Bedrock traffic goes through **Converse**, and its `bedrock-mantle` provider speaks only Mantle's OpenAI-compatible `/v1` routes, not `/anthropic/v1/messages` (section 3).
2. **Converse has no equivalent, definitively at the schema level.** Converse's `ContentBlock` and `ToolResultContentBlock` unions have no `tool_reference` or `tool_addition` member, `ToolSpecification` has no `defer_loading`, and Anthropic's pages say both tool search and mid-conversation system messages are "not available through the Converse API". A `cachePoint` in `toolConfig.tools` caches only the tool prefix: appending a tool after it still rewrites system and every message. What I could not settle without a call is whether `additionalModelRequestFields` would smuggle a `tools` array with `defer_loading` through Converse; even if it did, there is no message block to surface a deferred tool with, so it would not help (section 2.3).
3. **There is a cheaper second native form for model-driven activation: our own `search_tools` returning `tool_reference` blocks.** Anthropic's tool search accepts a client-side search tool whose `tool_result` carries `{"type": "tool_reference", "tool_name": ...}` blocks; the API expands them in place and "the prefix is untouched". This works on every model that has tool search (including Sonnet 5 and Haiku 4.5, which lack `tool_addition`) and on `bedrock-runtime` **InvokeModel** (not Converse). It is the native replacement for Z1's list append; `tool_addition` is the native replacement for application-driven changes (MCP connect, toggle, mode switch, C88).
4. **On local servers (llama.cpp, vLLM, Ollama) no provider route exists.** Common chat templates render tools at or near the start of the prompt (Qwen3 inside the first system turn, Llama 3.x in the system header and the first user turn, GPT-OSS harmony in the system and developer messages), and all three servers reuse KV only for a matching token prefix. A tool change re-prefills nearly everything. Route B is the only fix there, and it is also the only fix on Converse.
5. **OpenAI has a native form on the Responses API only.** `tool_search` (gpt-5.4 and later) with `defer_loading`, and an `additional_tools` input item (role `developer`) that adds tools at a point in the input; OpenAI says discovered tools are "injected at the end of the context window" so the cache survives. Removing a loaded tool "will break the model's cache from that point forward". Chat Completions has nothing like it.
6. **Route B is sound but not free of risk, and it is unmeasured.** The list never changes, so the cache and preserved thinking are safe everywhere. The costs are a nested `arguments` object without native schema enforcement, a dispatcher that must unwrap to the real name before every permission, role (TR1), hook, audit, checkpoint and display path, and a wire history that must keep `call_tool` as the tool name (Converse checks every `toolUse` name against `toolConfig`). Z4, the measurement that would say whether models call it well, has not run.
7. **Recommendation:** make the C88 "withheld" record the single source of truth for tool-set changes, then serialize it per provider: `tool_addition` / `tool_removal` on Anthropic-native paths (direct, Vertex, later Mantle Messages), C88 withheld semantics everywhere else; build Route B (Z3) for Converse and local only after #750 lands and the cheap half of Z4 shows models call it. Order and sizes in section 7, proposed rows in section 8.

## 2. Findings with citations

### 2.1 Anthropic: mid-conversation tool changes

Source: [Mid-conversation system messages and tool changes](https://platform.claude.com/docs/en/build-with-claude/mid-conversation-system-messages), fetched as markdown.

- **What it does.** "The `tools` array sits even earlier in the hashed request prefix than the top-level `system` field, so editing it invalidates the prompt cache for the entire conversation." Instead, "declare the full tool set in `tools` up front, then use `tool_addition` and `tool_removal` blocks to offer a tool to the model, or withdraw it, from a specific point in the conversation onward. The `tools` array itself never changes, so the cached prefix stays intact."
- **Shapes.** Both are content blocks of a `role: "system"` message and can be mixed with `text` blocks. By reference: `{"type": "tool_reference", "name": "..."}`; MCP tools by `mcp_tool_reference` or `mcp_toolset_reference`. By value (inline-tools beta only): `{"type": "tool_definition", "definition": {...}}`, where the definition is any `tools` entry and "replaces the earlier one from that position onward"; an identical definition "changes nothing, so a client can safely resend it".
- **Declared-only references.** "Referencing a name that is not declared in `tools` returns a 400 error (on the Claude API, with `error.details.error_code` set to `tool_reference_unresolved`)."
- **`defer_loading`.** "Every tool declared in `tools` is offered to the model from the start of the conversation unless it is declared with `defer_loading: true`, which keeps it withheld until a `tool_addition` block surfaces it." At least one non-deferred tool must stay in `tools` (a tool search tool counts), otherwise a 400, unless inline-tools is sent and a `tool_addition` exists, in which case "the first tool defined by value costs one full cache miss". "A deferred definition can't carry `cache_control`."
- **Placement.** A system message with content "must immediately follow a `user` turn (or an `assistant` turn ending in a server tool result). It must then end `messages` or be immediately followed by an `assistant` turn." A `tool_result` user turn counts. It "cannot sit between a `tool_use` block and its `tool_result`". `tool_addition` and `tool_removal` "are not accepted immediately after a paused `assistant` turn" (Limitations). Consecutive system messages are judged as one.
- **Caching.** "Append the system message after the breakpoint. Because it comes after the cached prefix, it does not change the prefix hash and the cache still hits." "`cache_control` goes on the block or in the definition, not both, and counts toward the request's breakpoint limit." Editing or removing a system message already sent invalidates the cache from there and, on Fable 5.2, Mythos 5.2, Fable 5.1, Mythos 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5, "the thinking blocks in every later assistant turn".
- **Limits.** A 400 `available_tools_limit_exceeded` above 10,000 deferred tools, above 10,000 tools defined after the first user message, or above 4 MB (4,194,304 bytes) of definitions sent after the first user message or of rendered tool text.
- **Models.** Fable 5.2, Mythos 5.2, Fable 5.1, Mythos 5.1, Fable 5, Mythos 5, Opus 5.5, Opus 5, Opus 4.8, Sonnet 5.5, Haiku 5.5. "This feature is not available on Claude Sonnet 5." The brief's model list matches, with Mythos 5 and 5.1 added.
- **Headers and platforms (the page's note, verbatim in substance).** "`inline-tools-2026-09-15` works on the Claude API, Claude Platform on AWS, Claude Models on Google Cloud (Anthropic managed), and Microsoft Foundry." "`mid-conversation-tool-changes-2026-07-01` works on Claude Models on Google Cloud (Google managed) and Amazon Bedrock, and on the four platforms listed for `inline-tools-2026-09-15`." Where both work, send `inline-tools`; it is a superset.
- **Bedrock, read precisely.** "Amazon Bedrock" on these pages links to [Claude in Amazon Bedrock](https://platform.claude.com/docs/en/build-with-claude/claude-in-amazon-bedrock), which "serves Claude through the Messages API at `/anthropic/v1/messages` on the `bedrock-mantle` endpoint". The `bedrock-runtime` endpoint has its own entry, "Amazon Bedrock (bedrock-runtime)", with the footnote "Through InvokeModel only (not Converse)" for mid-conversation **system messages**; the [bedrock-runtime page](https://platform.claude.com/docs/en/build-with-claude/claude-on-amazon-bedrock-legacy) documents system messages and per-message effort through InvokeModel and says nothing of tool changes, and adds: "For Converse API users: ... To add system instructions mid-conversation, use the InvokeModel API." So the brief's "available on the Messages-API endpoint (Mantle), not through the InvokeModel API" is correct for tool changes; system messages alone also work on InvokeModel.
- **Two catches on Mantle.** The Mantle page: "Claude Fable 5.2 and Claude Mythos 5.2 aren't available in Claude in Amazon Bedrock. Amazon Bedrock serves them on the `bedrock-runtime` endpoint only." So on Bedrock, Fable 5.2 has no `tool_addition` at all. And Mantle's "Features not supported" list includes server-side tools and the MCP connector, so `mcp_toolset` forms are out there.
- **A late tool without inline-tools.** [Change tools or instructions without failing the prefix check](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking/change-tools-or-instructions): "If you learn of a tool later, on a platform without the `inline-tools-2026-09-15` header: Add the tool to the end of `tools` with `defer_loading: true`, which isn't a change, then offer it by name." And: "A tool with `defer_loading: true` stays out of Claude's context and the prefix check until a message or tool search result refers to it. Until then, adding, updating, or removing it isn't a change. Afterward it is. Turning `defer_loading` on or off counts as changing `tools`, too." This is what makes Route A usable on Vertex and Mantle for MCP servers that connect late.
- **Discrepancy with the bundled claude-api skill.** Its platform table says mid-conversation tool changes are "No" on Foundry; the live page lists Foundry for both headers. The live page wins; I did not test Foundry (the fork has no Foundry provider anyway).

### 2.2 Anthropic: tool search, `defer_loading` and tokens

Sources: [Tool search tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-search-tool), [Tool use with prompt caching](https://platform.claude.com/docs/en/agents-and-tools/tool-use/tool-use-with-prompt-caching), [Prompt caching](https://platform.claude.com/docs/en/build-with-claude/prompt-caching).

- **Deferred tools are not in the rendered prefix.** "Deferred tools are not included in the system-prompt prefix. When the model discovers a deferred tool through tool search, the definition is appended inline as a `tool_reference` block in the conversation history. The prefix is untouched, so prompt caching is preserved."
- **But they are sent on every request.** "You still send every tool's full definition in the `tools` array on every request, including the deferred ones. The API needs them server-side to run the search and expand `tool_reference` blocks." So `defer_loading` costs request bytes (Bedrock caps a payload at 20 MB per the bedrock-runtime page; the 4 MB rendered-tools cap above applies) but not input tokens until surfaced.
- **Once surfaced they are billed.** "Tool search isn't metered as a separate server tool ... the tool definitions that search loads into context count as input tokens like any other tool definition." The tool-changes page does not state billing for a `tool_addition` directly; it says "only the appended message is processed as new input", which I read as: the surfaced definition is billed once as uncached input at its position, then read from cache on later turns. That reading is **inferred**, not quoted; a `count_tokens` call with and without the addition would settle it for cents.
- **Custom client-side search.** "You can implement your own tool search logic ... by returning `tool_reference` blocks from a custom tool": a standard `tool_result` whose content is `[{ "type": "tool_reference", "tool_name": "discovered_tool_name" }]`, with every referenced tool declared in `tools`, "normally with `defer_loading: true`". "The API expands `tool_reference` blocks throughout the conversation history, so Claude can reuse discovered tools in later turns without re-searching."
- **Models and platforms for tool search.** Every listed current model, including Sonnet 5, Opus 4.6 to 4.8, Sonnet 4.6, Haiku 4.5 and Opus 4.5 (not Opus 4.1 and earlier). Platforms: Claude API, Amazon Bedrock (Mantle), Claude Platform on AWS, Google Cloud (Google managed), Foundry, and bedrock-runtime with the footnote "On Amazon Bedrock it is not available through the Converse API." The warning box: "On Amazon Bedrock, server-side tool search is available only through the InvokeModel API, not the Converse API."
- **Caching rule that bites.** "A tool with `defer_loading: true` can't also carry `cache_control`: the API returns a 400. Put the cache breakpoint on a non-deferred tool." This is the M8 bug Z5 recorded: `markLastToolForCache` (`core/llm/llms/anthropicCache.ts`) marks `tools[tools.length - 1]` unconditionally.
- **Strict mode.** "The grammar for strict mode ... builds from the full list of tools, so using `defer_loading` with strict mode doesn't make the API recompile the grammar."
- **Invalidation table.** "Modifying tool definitions: Entire cache (tools, system, messages)" (Tool use with prompt caching).

### 2.3 Bedrock Converse

Sources: AWS API reference for [Converse](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Converse.html), [Message](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Message.html), [Tool](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_Tool.html), [ToolSpecification](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ToolSpecification.html), [ContentBlock](https://docs.aws.amazon.com/bedrock/latest/APIReference/API_runtime_ContentBlock.html); Anthropic's tool search and bedrock-runtime pages above.

- **No surface for a tool change.** `Tool` is a union of `toolSpec`, `systemTool` and `cachePoint`. `ToolSpecification` has `name`, `description`, `inputSchema` and `strict`, and nothing else: no `defer_loading`. `ContentBlock` members are text, image, document, video, audio, toolUse, toolResult, reasoningContent, citations, guardContent, searchResult and cachePoint: no `tool_reference`, no `tool_addition`. Converse cannot express a deferred tool or a surfaced one.
- **`role: "system"` exists in Converse messages.** The `Message.role` valid values are `user | assistant | system`. The fork already saw this live: "Converse accepts it only before an assistant turn (live, 2026-11-04)" (`plans/research/area-caching-cost-visibility.md` section 6.2, C8). That gives mid-conversation **instructions** a possible Converse form (the open K5 and "Converse system-role probe" rows), not tool changes, because a system message's content is still a `ContentBlock` list.
- **`additionalModelRequestFields`.** "Additional inference parameters that the model supports, beyond the base set of inference parameters that `Converse` and `ConverseStream` support in the `inferenceConfig` field." The fork already passes `anthropic_beta` there (`core/llm/llms/Bedrock.ts` near line 1575). Whether Bedrock would forward a top-level `tools` key with `defer_loading` from there, and how it would merge with `toolConfig`, is **unverified**; third-party reports describe Bedrock rejecting `defer_loading` on tool schemas with "Extra inputs are not permitted" ([claudeissues 82549](https://claudeissues.com/issue/82549-bedrock-gateway-mode-invalid-beta-flag-tools-n-custom-defer-loading-400s-from-cl), [claudeissues 25212](https://claudeissues.com/issue/25212-toolsearch-generates-tool-reference-blocks-on-bedrock-despite-api-incompatibilit); unofficial, possibly stale, and about other paths). It does not matter for the verdict: even a forwarded deferred tool has no Converse block to surface it with.
- **The `cachePoint` trick.** A `cachePoint` member at the end of `toolConfig.tools` (which the fork sends, `Bedrock.ts` line 1504 and adapter line 753) lets the tool definitions before it hit the cache. A tool appended after it keeps that part, but the tool region precedes `system` and every message, so system and the whole conversation are written again. It saves T (the tool tokens) and nothing of S (everything after). Not free.
- **Converse also checks tool names in history.** The fork's own comment (`core/llm/llms/Bedrock.ts:1642`): "toolResult blocks must follow valid toolUse blocks (which also verifies that the tool name is present in toolConfig)". This constrains Route B (section 5).
- **Preserved thinking on Bedrock.** The preserved-thinking pages list both "Amazon Bedrock" and "Amazon Bedrock (bedrock-runtime)" as supported with no Converse exception stated, so I treat the prefix check as applying to Converse traffic too (**inferred**). On Converse, today's "apply now" (editing `toolConfig.tools`) therefore risks a 400 on Fable 5.2 and Mythos 5.2 (every account) and a possible 400 on Opus 5.5, Sonnet 5.5, Haiku 5.5 and Fable 5.1 ([prefix checks](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking/prefix-checks), "What each model does when the prefix check fails"). That is a correctness reason for C88's deferral, independent of cost.

### 2.4 OpenAI

Sources: [Tool search](https://developers.openai.com/api/docs/guides/tools-tool-search.md), [Prompt caching](https://developers.openai.com/api/docs/guides/prompt-caching.md).

- "In the Responses API, only `gpt-5.4` and later models support `tool_search`." Mark functions or MCP servers with `defer_loading: true`; hosted mode (OpenAI searches the declared deferred tools) or client mode (`tool_search_call` / `tool_search_output`, echoing the `call_id`).
- Cache: "When new tools are discovered by the model, they are injected at the end of the context window." "All tools are loaded at the end of the model's context window ... This allows the model's cache to be preserved from one request to another."
- Application-driven addition: "you can use an `additional_tools` input item to make tools available at a specific point in the conversation", with `"role": "developer"` and a `tools` array; "Tools in an `additional_tools` item become available only after that item appears in the input." The caching page adds that "`additional_tools` input items do not currently accept `prompt_cache_breakpoint`".
- Removal: "If you want to disable a loaded tool, you can remove it from the `tool_search_output` item ... but note that changing the loaded tool set will break the model's cache from that point forward." So removal costs everything after the item that loaded the tool, not the whole prefix.
- Prefix rule otherwise: "Cache reuse requires the entire rendered prefix to match", and a change to "tool names, descriptions, schemas, ordering, or tool-specific instructions" breaks it; "Preserve tool definitions, ordering, and schemas." The guides document the Responses and Agents APIs only; I found nothing equivalent for Chat Completions.

### 2.5 Local servers and chat templates

- **Qwen3** ([`tokenizer_config.json` chat template](https://huggingface.co/Qwen/Qwen3-8B/raw/main/tokenizer_config.json)): with tools, the first turn is `<|im_start|>system\n{system}\n\n# Tools ... <tools>{one JSON object per tool}</tools> ...<|im_end|>`. The system text comes first, so a change from N to M tools keeps the system tokens and re-prefills from the first tool onward, which is every message. Going from zero tools to some changes `{system}<|im_end|>` into `{system}\n\n# Tools`, the same effect.
- **Llama 3.x** ([Llama 3.3 template](https://huggingface.co/unsloth/Llama-3.3-70B-Instruct/raw/main/tokenizer_config.json); [Meta's prompt format](https://raw.githubusercontent.com/meta-llama/llama-models/main/models/llama3_1/prompt_format.md)): any tools add `Environment: ipython` at the very top of the system header; custom tools go into the first user message by default (`tools_in_user_message = true`). Zero to some diverges at about token 5; N to M diverges at the first user message.
- **GPT-OSS harmony** ([format](https://raw.githubusercontent.com/openai/harmony/main/docs/format.md)): function tools are defined "in the developer message in a dedicated `Tools` section" (`namespace functions { ... }`), and the system message gains "Calls to these tools must go to the commentary channel: 'functions'." when functions exist. Both precede the conversation.
- **llama.cpp server** ([README](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md)): `cache_prompt` (default on) "Re-use KV cache from a previous request if possible. This way the common prefix does not have to be re-processed, only the suffix that differs". `--cache-reuse N` attempts to reuse chunks "via KV shifting" after a divergence (default 0, off); it can recover some later chunks but positions shift and it is not a guarantee. **Not measured here.**
- **vLLM** ([prefix caching design](https://docs.vllm.ai/en/latest/design/prefix_caching.html)): "we hash each kv-cache block by the tokens in the block and the tokens in the prefix before the block", with a parent hash per block, so a change in an early block changes every later block's hash (the page implies this by construction and does not say it in words).
- **Ollama**: its runner keeps per-slot input caches and reuses the longest matching prefix (`LoadCacheSlot` in [`runner/llamarunner/cache.go` at 0.5.13](https://cdn.jsdelivr.net/gh/ollama/ollama@0.5.13/runner/llamarunner/cache.go), seen through a search summary; the current tree moved this code and I did not read the current version, **unverified**). Templates are per model and follow the model's own format, so the Qwen3 and Llama placements above apply.
- **Consequence.** Locally the tool list is paid in time (re-prefill), on every change and on every request when nothing is cached. No server offers an append-only tool form. A byte-stable list (Route B) is the only way to keep the KV prefix.

## 5. Route B assessment (Z3 on top of Z8, Z10, Z11)

**Shape.** The list is: built-ins, MCP tools that fit the budget (name order), `search_tools` whose description lists every deferred name in a fixed order (Z10, PR #750), and one `call_tool` with `{name: string, arguments: object}`. A search result carries the found tool's name and full JSON schema as text. Activation never touches the list.

**Correctness risks.**

1. **Real-name resolution everywhere.** Every path keyed on `toolCall.function.name` must see the unwrapped name: the GUI policy evaluation (`gui/src/redux/thunks/evaluateToolPolicies.ts`), the CLI permission check, the TR1 execution refusal (`roleRefusal` in `core/tools/roleTools.ts`), hooks, the audit trail, injection flagging (`flagToolOutput` callers), checkpoints (`snapshotBeforeEdit` in `callToolById` keys on the edit tools), the approval card and the tool-call display. One missed path is a permission bypass: an MCP tool denied by name would run as `call_tool`. The fix is one unwrapping function at the boundary where a tool call enters the app (before policy evaluation), with a test per consumer that a wrapped call is treated exactly as the bare call. Built-in tools must never be callable through `call_tool` (refuse), so the indirection cannot launder a built-in denial.
2. **Wire history keeps `call_tool`.** The assistant `tool_use` must be replayed as `call_tool` with the nested arguments, byte for byte, or the prefix and preserved thinking break; and on Converse a `toolUse` whose name is not in `toolConfig` is rejected (fork comment, section 2.3). So the history stores the wire form and the UI shows the resolved form; the two must not be conflated in `ChatHistoryItem`.
3. **Schema validation moves to us.** The model fills `arguments` against a schema it read in a tool result, not one the provider enforces: no `strict: true` constrained decoding (Anthropic, Converse `ToolSpecification.strict`), no provider-side argument typing. Validate with the found tool's schema (`coerceArgsToSchema` already exists, `core/tools/callTool.ts:111`) and return a validation error naming the field; each error costs a turn.
4. **Blind calls.** A `call_tool` for a name no search in this conversation returned is refused (section 6.3 design); the activated set comes from the history (Z8), so resume and new sessions behave.
5. **Names.** Z11 (`server__tool` with a collision-free map back) matters more here: the model types the name as a string, so first-server-wins routing and lookalike names are a real ambiguity, not a cosmetic one.
6. **Model behaviour, unmeasured.** No evidence in the repo on how often models nest arguments correctly, hallucinate a name, or call the real name directly after reading its schema. The last is likely on models trained on native tool calling and must be handled: a direct call to a deferred real name is either refused with a hint to use `call_tool`, or accepted as text recovery, and the choice needs Z4 data. Small local models are where this is most likely to fail and also where it pays most.

**Cost.** `call_tool` is a short permanent definition (estimate about 80 to 120 tokens, by the fork's 100 to 125 per MCP tool, Z0); the schema in the search result costs k once (the same k as appending the tool, but uncached once instead of forcing S + C + k to be rewritten); each call adds a few tokens of wrapper. Against today's activation cost from section 6.3, (S + C + k) x (w - r), Route B turns the late-activation break-even of about 175 requests (Opus 5.5 and Sonnet 5.5 at read 0.05, S = 40k) into a gain from the first request after activation, and locally removes the re-prefill entirely. It also makes the tool search budget question (Z9) much less sensitive, because deferral no longer has a rewrite penalty.

**Which models.** All of them, which is its point: Converse Claude, Nova, Qwen, Llama, GPT-OSS on Mantle `/v1` and local servers. On Anthropic-native paths Route A is strictly better (native schema, native validation, no unwrapping), so Route B should be off there.

## 6. Route A: how the request builders would change

### 6.1 One internal record, two serializations

Add an append-only tool-set event to the conversation (proposed row MT1): `{kind: "add" | "remove", names, reason, at: message index}`, written by the C88 machinery when a tool is enabled, disabled, denied, toggled, an MCP server connects or disconnects, or the mode changes. The C88 "withheld" state is this record read on a provider without Route A. On a provider with Route A the same record becomes a `role: "system"` message carrying `tool_addition` / `tool_removal` blocks. The record, not the live tool list, is the source of truth, so both surfaces (IDE and CLI) and both routes agree, and resume replays it.

### 6.2 Anthropic-native builders (direct, Vertex, later Mantle Messages)

1. **Declared set.** At the first request of a conversation, `tools[]` is the union of tools the session may offer: the current mode's offered set (TR1) non-deferred, and everything else the session knows about (other modes' tools, disabled MCP tools, MCP tools over the Z1 budget) with `defer_loading: true`. Store the array as sent and replay it verbatim. A tool that becomes known later (a late MCP server) is appended to the end with `defer_loading: true`, which the docs say "isn't a change", then referenced. Never remove an entry, never flip `defer_loading` on an entry already sent (that "counts as changing `tools`"), never edit a description (a refreshed listing is a by-value redefinition under inline-tools, or frozen text elsewhere).
2. **The system message's position relative to breakpoints.** It goes after the newest user message (the `tool_result` turn in a loop), last in `messages`. `markCacheBreakpoints` marks the last blocks of the last two user-role messages, so this request reads the previous entry at the second-to-last user message and writes at the last user message, which sits **before** the system message. The tool change itself is then uncached input this turn and is covered by the next turn's breakpoint on the following user message. Two code changes: the builders must stop folding a mid-conversation system message into top-level `system` (they filter every `system` role today), and `markCacheBreakpoints` must skip a system message (it only marks `user` roles already, so it does). Optionally put `cache_control` on the tool block when the system message is the last item, counting toward the four breakpoints.
3. **Breakpoint on tools.** `markLastToolForCache` must mark the last **non-deferred** tool (Z5's M8 bug; a deferred tool with `cache_control` is a 400).
4. **Beta header.** Send `inline-tools-2026-09-15` on the Claude API (and Claude Platform on AWS); `mid-conversation-tool-changes-2026-07-01` on Vertex (as `anthropic-beta`) and Mantle. Gate by model: only the models in section 4; others fall back to C88 withheld semantics with the record in 6.1.
5. **Placement guards.** Never emit a tool change between a `tool_use` and its `tool_result`, nor right after a paused server-tool turn; if the change arrives mid-round, queue it until the next user message exists (the same rule `change-tools-or-instructions` gives: "when Claude's turn is last, wait until the next user message is in place").
6. **Compaction.** The fork's compaction is client-side (summary replaces history). The tool-change messages inside the summarized range vanish with it, so at compaction fold the net record into a freshly built `tools[]` for the new conversation; the cache is cold there anyway, which is exactly C88's "apply at the next cold cache". (Server-side on-demand compaction with inline-tools carries `tool_changes` in the block, but the fork does not use it.)
7. **Execution still refuses.** The docs warn a system message "doesn't guarantee that Claude follows an instruction, so apply limits ... in the code that runs your tools". TR1's executor refusal and C88's refusal at execution stay; a call to a removed tool gets the same refusal text.

### 6.3 Interplay with C88 "withheld"

- Without Route A, C88 keeps a disabled tool in the list and refuses at execution until the next cold cache. With Route A, the same event becomes a `tool_removal` now: the model stops seeing the tool and the refusal path becomes a backstop. Enabling a tool is symmetric: C88 cannot offer a new tool until the cold cache; Route A offers it now by `tool_addition` if it was declared (deferred) at the start or appended deferred later.
- The C80 cost warning should read "free on this model" when the active provider and model support Route A, so the user is not warned about a cost that will not occur.
- On Converse, C88's deferral is also a correctness measure (section 2.3, preserved thinking): "apply now" by editing `toolConfig` on Fable 5.2 or Opus 5.5-class models must either strip earlier thinking blocks or not happen.

### 6.4 Interplay with TR1 role tables

TR1 defines the offered set per role and mode. Route A changes what "offered" means on the wire: `tools[]` is the declared set (a superset, fixed per conversation) and the offered set is the declared set narrowed by the tool-change record. A mode switch (Plan to Agent) is a `tool_addition` of the agent-only tools rather than a new list, which also fixes the cache cost of mode switches on Anthropic paths. The TR1 executor refusal must check the role's offered set at the time of the call, not the declared set, or a deferred-but-declared tool could be called by name after a removal. A test should assert that the reviewer, summarizer and other no-tool roles still carry no `tools[]` at all (TR1's existing test), since declaring a superset there would be a regression.

### 6.5 Preserved thinking

On Fable 5.2 and Mythos 5.2 every account fails the prefix check with a 400, and on Fable 5.1, Opus 5.5, Sonnet 5.5 and Haiku 5.5 the result is a possible 400 ([prefix checks](https://platform.claude.com/docs/en/build-with-claude/preserved-thinking/prefix-checks)). Editing `tools[]` invalidates every thinking block minted before the edit ("One reworded sentence in a description is enough"). Route A is the documented fix, and its rules are the ones above: declare once, never edit, append changes, never delete or reword an appended tool-change message. A deferred tool is outside the comparison "until a message or tool search result refers to it". This makes Route A more than a cost saving on those models: today's "apply now" on direct Anthropic is a latent 400.
