# Web search: providers, a privacy-first default and user-configured backends (2026-11-15)

Status: research and design only, written against `main` at `78212ee68` (merge of #907). No code was changed, nothing was built or measured, no paid API was called and no account was opened. Vendor pages were read live on 2026-11-15; each is cited by URL in section 12 and marked P (primary: vendor documentation, terms, pricing page) or S (secondary: press, trackers, third-party guides). A claim that rests only on S sources says "unverified". "Quality" figures are expectations, not measurements: WB66 measures them.

This note extends three baselines and does not repeat them:

- `plans/research/web-search-and-fetch.md` (2026-11-11): the first backend inventory, the `WebSearchProvider` sketch (§7.1) and the query-privacy gate (§6, built as WB3).
- `plans/research/web-fetch-deep-dive.md` (#898): rows WB17 to WB36, the `web:` section (§8.1), the fetch record and provenance (§7.8, WB24).
- `plans/research/web-fetch-large-pages-and-policy.md`: rows WB37 to WB52, the typed outcomes (§6) and the Web policy area (§8, WB45).

The largest WB row in either note is WB52, so the rows proposed here start at WB53. The decided rows that bind this note are in `plans/decisions-2026-11-15.md` §4: WB1 (configured or hidden, no default backend), WB3 (refuse a secret in a query, ask on a path or code), WB7 (spotlight on for web results), WB10 (provider-native search opt-in per model, with a consent line naming the provider).

The owner's ask, 2026-11-15:

> What other web-enabled tools do gateways typically provide? Is there a search? Can we find a default search provider that would respect privacy while still providing good results, and maybe also options for the user to configure a different search provider? Google search may have a way of supporting OAuth-based search, or possibly an API key provided by the user (or a customized search, but this will be seen as spying by users... so better to let them set their own).

The owner also ruled out running or branding a search proxy of our own. The upstream Cloud Run proxy was removed in #627 for exactly that reason (`PRIVACY.md`, "Older builds").

## 1. Summary

**What gateways offer beyond fetch.** Every major model API now runs search on its own servers:

- Anthropic `web_search` and `web_fetch`;
- OpenAI Responses `web_search`, with `open_page` and `find_in_page` actions;
- Gemini `google_search` and URL context;
- xAI `web_search` and `x_search`;
- Mistral `web_search` and `web_search_premium`.

Two gateways add search that works with any model:

- **OpenRouter:** the `openrouter:web_search` server tool, with native passthrough or Exa, Firecrawl, Parallel or Perplexity behind it.
- **Vercel AI Gateway:** Perplexity, Exa, Parallel, Browserbase, DeepSeek and Tako search tools, plus Browserbase fetch.

AWS has no Claude server tool on Amazon Bedrock. It sells Web Search on Bedrock AgentCore instead: an Amazon-operated index exposed as an MCP target, at $7 per 1,000 queries. Cloudflare's contribution is on the fetch side: Markdown for Agents answers `Accept: text/markdown`.

Beyond plain search, the same vendors sell news, images, video, places, crawl, extract, screenshots, browser sessions, "answer" endpoints and deep-research jobs (section 2). For an IDE and terminal coding agent, only **web search** (with a freshness filter and a single-site filter) and the **fetch** we already have belong in the product. Code search, docs search, academic search and browser automation are reached through MCP servers the person adds. The rest is out, each for a stated reason.

**The default** (section 4). Search stays **off until the person picks a provider**, as decided in WB1. What changes is that picking is one click, and the choices are ordered by privacy:

1. **Your model provider's own search**, when the selected model has one. The query goes only to the provider that already receives the whole conversation. No new account, key or party is involved, and it costs a known amount per search ($10 per 1,000 on Anthropic). It is not available for Claude on Amazon Bedrock, on local models, or on most OpenAI-compatible endpoints.
2. **Brave Search API with your own key.** It has its own independent index and a stated 90-day log retention, and Brave says queries are never trained on. It costs $5 per 1,000 searches, with $5 of free credit a month, and a card is required.
3. **Your own SearXNG.** It needs no account or key and has no vendor log. The upstream engines see the queries, coming from the instance's address.

Mojeek, Kagi, Tavily, Exa, a custom JSON endpoint and any MCP search tool are on the list as well. Each one shows a fact line about what it does with your queries.

**Google** (section 5.1). There is no OAuth sign-in that gives a third-party client Google web results for its users:

- The Custom Search JSON API takes an API key plus a search engine ID. It is **closed to new customers**, and existing customers have until **2027-01-01**.
- Google's "Web Search Service" API takes a partner client ID and the end user's IP address. It is a partner product, not self-serve.
- OAuth does work for the Gemini API and for Vertex AI. There, Google Search reaches a person only as grounding for a Gemini model, which is the same thing as option 1 for a Gemini user.

The Bing Search APIs were retired on 2025-08-11. DuckDuckGo has no web-results API.

**Keys** go to the IDE's secret storage, or to `~/.continuous/.env` in the CLI, through the same `storeSecret` path as the provider setup. `config.yaml` holds only `${{ secrets.NAME }}`. **The home for all of this** is a **Search** section on the Settings > Web page (WB28), with a "Test a search" button. Settings > Providers shows a "native search" badge on providers that have one and links to it.

**Schema** (section 6): the as-built `web.search.{provider, url, apiKey}` keys keep their meaning, and new keys are added beside them. **Tool shape** (section 7): `search_web(query, freshness?, site?)` returns a provenance line, numbered spotlighted results, and typed outcomes on failure.

**The build plan** (section 10) has 15 rows, WB53 to WB67, in four parallel groups. **Kept for the owner** (section 11) is short:

- whether to open the vendor accounts that the quality measurement (WB66) needs;
- whether the project ever wants a vendor relationship (Google partner access, Brave attribution). The recommendation is no.

## 3. Provider matrix

### 3.1 How to read it

- **Who sees the query** is the set of parties beyond the person's own machine. With a client-side provider (one that runs on the person's machine and calls a search API), the model provider has already seen the query as model output; the search vendor is added to that. With native search, no one is added to the person's existing provider, though that provider may use its own subprocessor.
- **Identity** is what the vendor can tie a query to: an account and key, plus the person's IP address for any client-side call. SearXNG shows the instance's address instead.
- **Third-party client** means: may a person use their own key in an open-source client that they run themselves? Every vendor here licenses the key holder. None licenses us to hand out a key, and Brave's §4(a) forbids sharing one.
- **Quality for coding** is unmeasured. The entries say what to expect and why; WB66 measures it.

## 4. The default

### 4.1 The rule and the options

The record's rule is "no new egress by default", and privacy comes first (`decisions-2026-11-15.md` §4, WB1 and WB10). The owner adds "while still providing good results". Four shapes were considered:

| Option                                                    | New egress by default                                                                                        | Privacy                                                                                          | Results             | Verdict                                                                                                                                                         |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------ | ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A. A bundled key of ours to Brave or Mojeek               | yes                                                                                                          | every person's queries pooled on one account we hold; we become the operator the owner ruled out | good                | **Rejected.** Brave §4(a): the key "may not [be shared] with any third party". It would be a search service of ours in all but name, which is what #627 removed |
| B. A public SearXNG instance                              | yes                                                                                                          | a stranger's server sees every query; public instances often disable JSON                        | unreliable          | **Rejected**                                                                                                                                                    |
| C. Native search on by default where the model has it     | no new host, but a new paid action the person did not choose, and a call our gates cannot see before it runs | best: no added party                                                                             | good                | **Rejected as a default** (WB10 says opt-in), **kept as the first recommendation**                                                                              |
| D. **Off until the person picks**, with a one-click setup | none                                                                                                         | the person chooses the party, and sees its facts first                                           | as good as the pick | **Chosen**                                                                                                                                                      |

### 4.2 Decision

**SP-1. The default is off.** Until a provider is picked, `search_web` and `@web` are not offered, as today. No search host is contacted, and nothing about search appears in the tool list.

**SP-2. Picking is one step, and the choices are ordered by privacy.** The Settings > Web > Search section (WB63), and the `continuous search setup` command in the CLI, list providers in this order. The first available one is pre-selected:

1. **"Your model's own search (Anthropic)"**, shown when the selected model's provider and platform support native search (section 4.3).
   - The fact line reads: "Queries go only to Anthropic, which already receives this conversation. $0.01 per search on your Anthropic bill. Continuous cannot review a query before Anthropic runs it."
2. **"Brave Search (your key)"**.
   - The fact line reads: "Brave's own index. Brave keeps query logs up to 90 days and says it does not train on them. $5 per 1,000 searches after $5 of free credit a month; a card is required at sign-up."
3. **"SearXNG (your server)"**.
   - The fact line reads: "No account. The search engines your server queries see each query, from your server's address."
4. Below a divider, in this order: Mojeek, Kagi, Tavily, Exa, Custom endpoint, An MCP server's search tool. Each has a fact line from section 3.2. Tavily's and Exa's say what their privacy policies say about using queries.

**SP-3. Why native comes first.**

- On privacy it adds no party: the model provider has the conversation already, and the query is a summary of it.
- It needs no account, key or card.
- Its cost is a known line on a bill the person already pays.

Its weakness is that WB3's gate cannot review the query before the provider runs it. That gate exists to stop context from leaking to a _new_ party, and here there is none. So the trade is acceptable once it has been disclosed: the fact line says so, and WB10's consent line names the provider.

**SP-4. Fallback when native is not available.**

- `web.search.fallback` names a client-side provider for models without native search: Bedrock, local models, OpenAI-compatible endpoints.
- With no fallback set, such a model gets no search tool. The tool list then says nothing about search, and `@web` explains why.
- The setup offers to set the fallback, pre-selecting Brave if a Brave key is stored and SearXNG otherwise.

**SP-5. No vendor is called "the default" in docs or UI.** The order in SP-2 is the recommendation. Docs say "recommended", never "built in".

**SP-6. Bedrock users.** The setup offers "AWS Web Search (AgentCore)" through the MCP adapter (WB57). The fact line reads: "Queries stay in AWS. $7 per 1,000. Needs an AgentCore Gateway you create." It is listed under SearXNG, because it needs AWS setup the person must do.

### 5.4 Keys and where they live

- **SP-7. Secret storage only.**
  - The setup (Settings or `continuous search setup`) stores the key with `storeSecret` (`core/config/secretStorage.ts`): VS Code secret storage when `isSecureStorageAvailable`, otherwise `~/.continuous/.env`.
  - It then writes `apiKey: ${{ secrets.<NAME> }}` into the personal `config.yaml`. The name is `<PROVIDER>_SEARCH_KEY`, for example `BRAVE_SEARCH_KEY`.
  - This is the provider setup's pattern (`moveCredentialsToSecrets`), reused.
- **SP-8. A literal key in `web.search.apiKey`** is read in 2.28.x with a `continuous doctor config` warning. Settings shows a "Move to secret storage" button. From the next minor release it is refused at load, with that message. This applies the decision record's "never inline" to a key that #903 already accepts.
- **SP-9. `CONTINUOUS_WEB_SEARCH_KEY`** stays an accepted source for two releases, as #903 maps it. The environment is not a file in the repository.
- **SP-10. Keys never leave their endpoint.**
  - The guarded fetch drops `Authorization` and caller-named headers on a cross-origin redirect (#908).
  - Error text never quotes a response body (#908).
  - The audit line records the provider and host, never the key.

### 5.5 Where the settings live

- **SP-11. Settings > Web > Search** is the home. It is the WB28 page, and this section joins it. It holds:
  - the provider picker with the fact lines (SP-2);
  - the key field (it stores to secret storage and shows "stored in VS Code secret storage", never the value);
  - the URL field for SearXNG or custom;
  - the fallback select;
  - results per search;
  - the monthly limit;
  - this month's count and estimated cost;
  - **Test a search**.
- **SP-12. Settings > Providers** shows a "Web search: available" badge on a provider whose selected models support native search. The badge links to Settings > Web > Search. No search key is entered on the Providers page, because a search provider is not a model provider. The one exception is native search, which uses the model's existing key and needs none.
- **SP-13. Test a search.**
  - It sends the fixed query `continuous search test`, never text from the person.
  - It reports `ok` with the result count and latency, or one failure class: DNS, TLS, 401/403 (bad key), 403 with SearXNG ("JSON format not enabled"), 402 or credit exhausted, 429 with `Retry-After`, 5xx, timeout, or a body that is not JSON.
  - A native-search test spends one search, and the button says "$0.01" first.
  - The CLI equivalent is `continuous test-connection --search` (WB4's planned command).

## 6. Proposed `web.search` schema extension

It is compatible with #903 as built (`packages/config-yaml/src/schemas/web.ts:123-130`, `core/util/webConfig.ts:423-437`):

- `provider`, `url` and `apiKey` keep their names and meaning;
- a block with a `url` and no `provider` is read as `searxng`, which is what the backend does today;
- the environment variables still map in.

```yaml
# ~/.continuous/config.yaml (personal). Every key under web.search is personal-only, as #903 already reads it,
# except those marked [T]: any config (workspace, assistant, organisation) may set those, and only to tighten.
web:
  search:
    provider: brave # off | native | searxng | brave | mojeek | kagi | tavily | exa | custom | mcp   [T: off]
    url: "" # searxng and custom: required. Others: an optional base URL override (an enterprise egress proxy)
    apiKey: ${{ secrets.BRAVE_SEARCH_KEY }} # secret reference only (SP-8)
    fallback: searxng # with provider: native, used for a model without native search; default none
    fallbackUrl: http://127.0.0.1:8888 # url for the fallback when it needs one
    fallbackApiKey: "" # key for the fallback when it needs one
    maxResults: 5 # 1..10 [T: lower]
    maxPerTurn: 5 # searches per agent turn; also native max_uses [T: lower]
    monthlyLimit: 0 # 0 = none; a local count, refused past it with quota-exhausted [T: lower]
    country: "" # ISO 3166-1 alpha-2, sent only when set (Brave country, Anthropic user_location.country)
    safeSearch: moderate # off | moderate | strict, where the provider has it [T: stricter]
    native:
      dynamicFiltering: false # Anthropic: true uses code-execution filtering (not ZDR-eligible)
      google: standard # standard (Grounding with Google Search) | enterprise (Web Grounding for Enterprise, Vertex only)
      openrouterEngine: native # native | exa | parallel | perplexity | firecrawl
    custom:
      method: GET # GET (SearXNG shape) | POST ({"q": …})
    mcp:
      server: brave # a configured MCP server's name
      tool: brave_web_search # the tool to call
```

Reading rules:

- **SR-1.** `provider: off`, or `web.enabled: false`, from any source turns search off. Every other key is read from the personal file only. A workspace file cannot name a provider, because that would send the person's queries to a host the repository chose.
- **SR-2.** With `provider` unset, a present `url` means `searxng`. With both unset, search is off. This preserves #903 and #627 behaviour.
- **SR-3.** `apiKey` must be a `${{ secrets.… }}` or `${{ env.… }}` reference (SP-8). An `apiKey` with `provider: searxng` is still sent as a bearer token, as today.
- **SR-4.** `country` is never inferred from the OS locale or IP. An empty value sends nothing.
- **SR-5.** Per-model overrides ride on the model entry: `capabilities.webSearch: native | off`, which is WB10's per-model opt-in. It wins over `web.search.provider: native` for that model only.
- **SR-6.** Unknown `provider` values fall back to off and are reported by `continuous doctor config`.

## 7. The tool and its result

### 7.1 Definition

```ts
// core/tools/definitions/searchWeb.ts (proposed)
{
  name: "search_web",
  description:
    "Search the web. Use for errors, APIs, releases or facts newer than your training or specific to a project. Returns titles, URLs and short snippets; read a page with fetch_url_content.",
  parameters: {
    type: "object",
    required: ["query"],
    properties: {
      query: { type: "string", description: "Keywords, at most 400 characters. Do not include secrets, file paths or code." },
      freshness: { type: "string", enum: ["day", "week", "month", "year"], description: "Only results from this period." },
      site: { type: "string", description: "Only results from this host, for example docs.python.org." },
    },
  },
  defaultToolPolicy: "allowedWithPermission", // the Web area decides (8.2 of the large-pages note); was allowedWithoutPermission
}
```

The description is static and short, because the tool list is in every request's cached prefix (Track Z). It does not name the provider. The provider appears only in results, so changing providers does not invalidate the prefix.

### 7.2 Success

```text
[searched brave (api.search.brave.com) · 5 results · freshness: month · 2026-11-15T10:04:12Z · 412 ms · query sha256:9c1e04a7b2d3]
<untrusted-web-results>
1. asyncio.TaskGroup — Python 3.14 documentation
   https://docs.python.org/3/library/asyncio-task.html#task-groups
   2026-10-07 · "An asynchronous context manager holding a group of tasks. Tasks can be added to the group using create_task(). All tasks are awaited when the context manager exits." …
2. …
</untrusted-web-results>
```

- **Provenance line.** It carries the provider id, host, count, filters applied (a filter the provider ignored is shown as `freshness: ignored`), UTC time, duration and a hash of the query. It never carries the query text, because the model has it already and the audit line has it masked. It matches #908's `[fetched …]` line in form. WB24 already records `purpose: "search"`, `origin: "config"`.
- **Spotlight.** The whole block is spotlighted (WB7, on for web results). Title and snippet are attacker text.
- **Each hit:**
  - title, at most 120 characters;
  - URL, canonicalised, with `utm_*`, `gclid`, `fbclid` and `ref` removed, at most 300 characters;
  - the published or page date when the provider gives one;
  - snippet, at most 300 characters, cleaned of zero-width, bidi and tag characters (#898 7.7).
- **Deduplication and order.** Results are deduplicated by URL, the provider's order is kept, and nothing volatile appears inside the block.
- **Filtering.** A result whose host is denied by a `host:` or `net:` rule is dropped, and the provenance line says `2 dropped by your rules`.
- **Seen URLs.** Every result URL enters the session's seen-URL set with origin `search-result` (#898 7.9). Fetching it is then model-origin, with robots checked (RB-4).
- **Size.** Five results are about 300 to 450 tokens (estimate; WB66 measures it). This replaces today's 8,000 characters per result, which came from the backend's `content` field (`searchWeb.ts:5`).

### 7.3 Outcomes

Failures are results, not exceptions. They use the outcome vocabulary of the large-pages note (§6.2, WB41) and its rule that each outcome says whether a retry can help:

| Code              | When                                                                                    | Text to the model (exact)                                                                                                                          |
| ----------------- | --------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `refused-query`   | WB3: the outbound scan found a secret                                                   | "Search refused: the query contains a credential-shaped value. Rewrite the query without it. Do not retry unchanged."                              |
| `needs-approval`  | WB3 ask (path, code, over 400 characters) refused unattended, or declined by the person | "Search not run: the query contains a file path or code and was not approved. Search for the error text or API name only. Do not retry unchanged." |
| `blocked`         | Web level Off for a call that still arrived; Listed and the backend host not allowed    | "Search is turned off by your Web setting. Do not retry."                                                                                          |
| `turn-limit`      | more than `maxPerTurn` searches this turn                                               | "Search limit for this turn reached (5). Use the results you have, or fetch one of them. Do not retry this turn."                                  |
| `repeat`          | the same query and filters already answered this session                                | the earlier result, with "(answered from this session's earlier search; no new request was made)"                                                  |
| `quota-exhausted` | `monthlyLimit` reached, HTTP 402, or the provider's credit-exhausted error              | "Search quota is used up (<provider>). Tell the person; it resets <date or 'when credit is added'>. Do not retry."                                 |
| `rate-limited`    | HTTP 429 or the provider's rate error                                                   | "Search rate-limited by <provider>; retry after <n> s." (`Retry-After`, both forms; at most one automatic retry, as WB25)                          |
| `auth-failed`     | HTTP 401, or 403 that is not SearXNG's JSON 403                                         | "Search failed: <provider> rejected the key. Tell the person to check it in Settings > Web > Search. Do not retry."                                |
| `not-enabled`     | SearXNG 403 on `format=json`                                                            | "Search failed: the SearXNG server does not allow JSON results. Tell the person to enable json under search.formats. Do not retry."                |
| `backend-error`   | 5xx, DNS, TLS, connection                                                               | "Search failed: <class> at <host>. One retry may help; do not retry more than once."                                                               |
| `timeout`         | the deadline passed (the fetch limits' `timeoutSeconds`)                                | "Search timed out after <n> s at <host>. One retry may help."                                                                                      |
| `bad-response`    | the body is not JSON, has the wrong shape, or is over the byte cap (#908)               | "Search failed: <host> returned a reply that is not search results. Do not retry."                                                                 |
| `no-results`      | a successful search with zero hits (not an error)                                       | "No results for this query. Try fewer or different keywords."                                                                                      |
| `unsupported`     | native requested where the platform has none, and no fallback                           | the tool is not offered at all, so this appears only for a stale call: "Search is not available for this model. Do not retry."                     |

### 7.4 Native search results

Native search does not go through `search_web`. The provider tool (Anthropic `web_search`, OpenAI `web_search`, `google_search`, xAI `web_search`, `openrouter:web_search`) is attached to the request in its place. Then:

- `search_web` is not offered at the same time, so the model has one search tool, not two.
- Server-tool blocks are kept verbatim through history, ageing, compaction and forks: `server_tool_use`, `web_search_tool_result` and its `encrypted_content`, and `encrypted_index`. Changing them is a 400 on Anthropic. Track V's maskers skip them.
- The chat shows a "Searched the web with Anthropic" card with the query, the result titles and URLs, and `page_age`. Citations are rendered as links, as Anthropic and OpenAI require.
- An after-the-fact audit line records the provider, masked query, result URLs, time, and the count from `usage.server_tool_use.web_search_requests`.
- Result URLs enter the seen-URL set as `search-result`, so the fork's own fetch can open them under the usual rules.
- Errors arrive inside a 200 response (`too_many_requests`, `max_uses_exceeded`, `query_too_long`, `unavailable`) and are mapped onto the outcome codes above for the card. The model has already seen them.
- `allowed_domains` comes from the person's allow rules at the Listed level. `blocked_domains` comes from `host:` deny rules at every other level. Anthropic accepts only one of the two per request. When a deny list would make the request too large (`request_too_large`), the longest-matching 100 entries are sent and the card says so.

### 8.1 Policy: search follows the Web area

### 8.2 Provenance and spotlighting

Covered in 7.2 and 7.4. Every search, native or client-side, writes one record to the session fetch log (#908 `FetchLog`, `purpose: "search"`) and one masked audit line. The Browser panel (WB31) lists searches with the provider label.

### 8.3 Headless runs, CLI parity and workspaces

- **Headless (CO2).**
  - A configured provider counts as consent, because the person wrote it in their own file.
  - Anything that would ask is refused with `needs-approval`.
  - The start-up line names it: `Web search: brave (api.search.brave.com)`, or `Web search: native (Anthropic), $0.01 per search`.
  - `--max-budget-usd` counts search cost (8.5).
- **CLI parity.**
  - The terminal agent has no search tool today. `extensions/cli/src/tools/` has only `searchCode`, and the core `search_web` is IDE-side.
  - WB59 adds `SearchWeb` on the same core provider layer, with the same outcomes and a parity test over a fixture backend.
  - `continuous search setup`, `continuous test-connection --search` and `/web search <query>` complete it.
  - Gemini native search is IDE-only (WB62), because the CLI cannot render `search_suggestions` as provided. In the CLI, a Gemini model uses the fallback.
- **Per-workspace tightening only.** A workspace or assistant config may set:
  - `web.enabled: false`;
  - `web.search.provider: off`;
  - lower `maxResults`, `maxPerTurn` and `monthlyLimit`;
  - stricter `safeSearch`;
  - `host:` deny and ask rules, which drop results and feed `blocked_domains`.

  It cannot choose, add or change a provider, URL or key.

### 8.4 Egress

Each provider is opt-in egress. The provider rows (WB55 to WB57) and the docs row (WB65) change three places:

- **`core/egress/egress-allowlist.json`.** It gets one class `O` group: "Search providers the person picks in Settings > Web > Search; contacted only for searches after setup". The hosts are `api.search.brave.com`, `api.mojeek.com`, `kagi.com`, `api.tavily.com` and `api.exa.ai`. Native search adds no host. MCP and custom URLs are the person's own.
- **`PRIVACY.md`, "Contacts a third party only if you set it up".** The web search bullet becomes a short list:
  - one line per provider: what is sent (the query, filters, the key, the person's IP), what the vendor states about retention and training (section 3.2), and how to turn it off;
  - a native search line: "the query goes to your model provider as part of the model call; it may use its own search subprocessor".
- **`docs/customize/web-search.mdx`.** It is rewritten (WB15, absorbed into WB65) around the setup, the matrix and the "who sees the query" table.

### 8.5 Cost

- **SP-14. Every search has a cost line.**
  - A list-price data file (`core/llm/searchPrices.json`) is dated and sourced from the pages in section 12, with the same staleness test as the UA presets (WB49).
  - The cost counter shows searches as a separate line, priced by count: native from `usage.server_tool_use.web_search_requests`, client-side from the local count.
  - It is labelled "list price; free credits not tracked" for providers with a monthly credit (Brave, Exa, Tavily).
  - `--max-budget-usd` includes it.
  - OpenRouter's own `web_search` price comes from the catalogue it already reads (`core/llm/openRouterCatalog.ts`, the `webSearch` field).
- **SP-15. Free providers show $0.** SearXNG, custom and MCP have no price file entry, and the counter shows the count only.
- **SP-16. The cache cost of switching.** Turning native search on mid-session changes the tool list and so the cached prefix. C81 and C93 already plan the notice, and WB60 depends on C81.
