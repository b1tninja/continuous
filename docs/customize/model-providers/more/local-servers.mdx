title: "Local servers (OpenAI-compatible)"
description: "Use a model server on your machine, such as Strata, llama.cpp, vLLM, LM Studio or Ollama, through its OpenAI-compatible API."
---

Most local model servers have an OpenAI-compatible API. Continuous talks to all of them through the `openai` provider with the server's address as `apiBase`, which gives you chat, tool calls and agent mode.

## Set it up

1. Start your server.
2. Open **Set up models** (the model picker's **Manage models**, or the onboarding card) and choose **Local server (OpenAI-compatible)**.
3. Select **Detect**. Continuous looks for servers on the usual ports, including 8081-8089 for a second llama.cpp-style server, and fills in the address of the one it finds. You can also pick a usual address or type your own.
4. Select **Next**. The model list is read from the server, with the context window it reports. Choose the models and save.

The API key is optional: enter one only if your server was started with a key. It is stored as `CONTINUOUS_LOCAL_API_KEY`, apart from an OpenAI key.

## What is read from the server

The model list fills in what the server reports, so a saved model needs no editing:

- **Context window** (`contextLength`): `meta.n_ctx` (llama.cpp, Strata), `max_model_len` (vLLM), the loaded context from LM Studio's `/api/v0/models`, or `context_length`. For Ollama, only the context of a model that is loaded now (`/api/ps`): the trained maximum in `/api/show` is often larger than what Ollama runs with, and a larger window would have prompts cut short.
- **Tool calls** (`capabilities: [tool_use]`, for agent mode): `chat_template_caps.supports_tools` in `/props` (llama.cpp, Strata), `capabilities` in Ollama's `/api/show`, or LM Studio's `tool_use`. A template that takes tools does not guarantee a model that uses them well.
- **Images** (`image_input`): `modalities.vision` in `/props`, `architecture.input_modalities`, Ollama's `vision`, or LM Studio's `vlm` type.

When a server reports none of these, set them yourself.

## Configuration

```yaml title="config.yaml"
models:
  - name: Strata
    provider: openai
    model: <MODEL_ID>
    apiBase: http://127.0.0.1:8080/v1/
    contextLength: 524288
    capabilities: [tool_use]
```

`<MODEL_ID>` is an `id` from the server's `/v1/models`. Add `capabilities: [tool_use]` when the model supports tool calls, for agent mode.

## Why a turn re-reads the whole prompt

A local server keeps the previous request's prompt and answer in its cache and reuses the longest prefix the next request shares with it. A request that only adds messages reads just the new part: on a 400k-token session, about 23 s. A request that changes anything earlier makes the server read everything after the change again: at 400k tokens that is four to five minutes.

Where the change lands depends on the chat template. Qwen's template, which Strata and llama.cpp serve for the Qwen 3 models, puts the tool list first and the system message right after it, so a change to the system message is read as a change to the start of the conversation. Strata then reports that it reused about 16k tokens (one cache block: the tools) and read the rest.

Continuous builds every request as an extension of the previous one. The intended exceptions read the conversation again once: switching mode or model, applying a tool change (see [Changing tools during a session](/customize/deep-dives/prompt-caching#changing-tools-during-a-session)), compacting, and removing parts with **Choose what to keep**. Three ways the client changed earlier parts of the prompt were fixed after a session on 2026-11-15 in which 2 of 12 requests accounted for 99.8% of the prompt tokens read:

- A rule scoped to files (`globs`, `regex`) that a later message or tool result matched was added to the system message, in front of the whole conversation. Now the system message carries the rules that always apply and the ones the first message matched; a rule a later message or tool result matches is sent with that message, as a `<rule>` block after its content, and stays there.
- The rules in the system message followed the order the config listed them in, which a config reload can change. Two rules that swap places leave the prompt the same length but different after the tools. Rules are now sorted by file, name and text.
- **Try again** after a failed request (including the automatic retry after a timeout) re-sent the turn before it, or turned the tool result it was answering into an empty message. It now sends the failed request again unchanged. If the server dropped the failed request's cache (as it may when the client gives up while the prompt is still being read), the retry still reads the prompt once.

### When the conversation outgrows the window

Dropping the oldest messages changes the prompt right after the tools, so the server reads the whole conversation again. Until 2026-11-15 the amount dropped depended on the size of the latest turn, so the cut moved by a message or two on most turns and each move re-read the conversation: about 85 s for 394k tokens on Strata, every two or three turns.

Now nothing is dropped until the prompt passes 85% of the window on a local server (90% on a hosted provider). Then a whole block of the oldest messages goes at once, bringing the prompt down to 60% (65% hosted), and the conversation grows append-only, every request reusing the cache, until it reaches 85% again. The cut falls between messages and keeps each tool call with its result. In a compacted conversation the summary stays: it belongs to the head with the system message and tools, and blocks are counted from the turns after it. The context meter's line marks where the next block is dropped. The configured `maxTokens` is reserved for the reply, up to 10% of the window, instead of a fixed 1,000 tokens.

The window is counted with an estimate. For Qwen models the estimate uses the Llama 2 tokenizer, which counts about 23% more tokens than the server does, so pruning started about 97k tokens early on a 524k window. After each answered request to Strata, llama.cpp's `llama-server` or vLLM, Continuous compares the server's `prompt_tokens` with its own estimate of the same prompt and learns the ratio for that model (smoothed, between 0.6 and 2, with 5% headroom; one request outside 0.7 to 1.5 times the current ratio is ignored). These servers count the cached part of the prompt in `prompt_tokens`. Ollama's native count leaves it out, so Ollama, LM Studio and other servers are not calibrated. The ratio is kept until the editor restarts, so the first request after a restart uses the uncorrected estimate. A server that refuses a prompt as too long still shrinks the budget, and usage does not take that back.

When a request still re-reads much more than the part that changed, the cache-miss notice above the input names the first part of the prompt that differed from the previous request, for example `message 2 (your first message) changed: a user message`, or says that the prompt only grew and the server dropped its cache (another conversation used it, the model was unloaded, or the cache ran out of room). The webview's developer console has a `[prompt cache]` debug line per request with the positions and sizes, never the text.

The reused count comes from the response's `prompt_tokens_details.cached_tokens`, or llama.cpp's `timings.cache_n`. When the stream has neither and the server is Strata, Continuous reads Strata's `/metrics` once after the request for its `reused` count. Nothing is polled, and nothing is sent anywhere but the configured server.

### Planned compaction and the pre-warm

Past 70% of the window, the summary of the older turns is made in the background while you are idle (`contextManagement.plannedCompaction`, on by default for local servers). A line above the input says when it is ready. On a local server it waits for you: **Compact now** applies it, keeping the newest turns word for word, and the next message reads the summary and those turns once (about 12 s for 58k tokens on Strata). If the conversation reaches 85% first, or the last request already dropped the oldest messages to fit, your message waits and **Compact now (summary ready), then send** applies it at once; **Continue anyway** drops the oldest block instead. Nothing is re-read without you choosing it.

An agent working through tool calls, a Loop item and a resumed turn do not wait for you. When one of their requests would reach the limit (85% of the window, less the 5% the token calibration keeps in hand), the conversation is compacted first: with the summary ready it is applied at once; otherwise it is made then from the conversation the server already holds (about 80 s for a 6k-token summary, shown as "Generating conversation summary"; Stop stops it). The agent then carries on from the summary and the newest tool rounds. A long run that started from one message is cut at a tool round. After **Continue anyway**, or with `contextManagement.plannedCompaction: false`, the oldest block is dropped as before.

**Pre-warm (experimental, off by default).** With `contextManagement.prewarm: local`, once the summary is ready and you are still idle, the conversation as it will be after compacting is sent once to a Strata or llama.cpp server with a one-token reply, so the server has read it before your next message. That message then applies the summary with nothing to read again, and the line says "prepared and pre-warmed". On Strata the request carries `strata_prefix: {"messages": 2}`, which pins the server's checkpoint at the end of the summary, and it is skipped when `/v1/status` reports less free memory than it could take (about 7 GB per 390k tokens of the conversation it replaces, plus the checkpoints). Typing or sending stops it. Turn it on only after checking it on your server:

1. In a new, small conversation (not one whose cache you need), set the model's `contextLength` to about 40000 for the check, so the plan starts early. Keep Strata's `--prompt-cache` at 3 or more (the default is 6).
2. Chat until the context meter passes 70% and leave the window idle for 10 s. The line says "Compaction prepared", then "prepared and pre-warmed".
3. Open the server's `/metrics`: the newest request has `output_tokens` 1, and Strata's log has no `strata_prefix … ignored` line.
4. Send a message. Its `/metrics` entry should show `reused` about the pre-warm's `prompt_tokens` and `prompt_read` about the size of the new message.
5. Edit the newest turn and send again: `reused` should be about the size of the system prompt and the summary, not 16,384.
6. Start typing during a pre-warm: the request is cancelled and sent again at the next pause.
