## Quick start

1. In the [Bedrock console](https://console.aws.amazon.com/bedrock), open **Model access** and enable the models you want in your region.
2. Pick an authentication method below (an API key is the fastest).
3. Add a model to `config.yaml`:

```yaml title="config.yaml"
name: My Config
version: 0.0.1
schema: v1

models:
  - name: Claude Sonnet
    provider: bedrock
    model: anthropic.claude-sonnet-4-6
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
    env:
      region: us-east-1
      crossRegionInference: auto
    roles:
      - chat
```

## Add Bedrock from the UI

Open the model selector, choose **Add Chat model**, and pick **Amazon Bedrock**:

1. Choose how to authenticate (API key, AWS profile / SSO, access keys, or default credentials) and fill in the fields that appear.
2. Pick your **AWS region**.
3. Click **Test connection**. Continuous lists the models your account can use in that region, including inference profiles and your own application inference profiles, and the **Model** list above fills with them (newest first, legacy models last). The refresh icon next to **Model** reloads the list.

   If you signed in with a **Bedrock API key**, Continuous also asks the Mantle endpoint (see [Bedrock Mantle](#bedrock-mantle-openai-compatible-endpoint)) and adds the models that only it serves, labelled **· Mantle**. A model both endpoints serve is listed once, on the standard endpoint. When you pick a Mantle-only model, Continuous saves it with the `bedrock-mantle` provider using the same key and region, so you do not need to switch providers. Profile, SSO and access-key sign-ins cannot call Mantle, so those lists show standard-endpoint models only.
4. Click **Send test message** to confirm the model actually answers (this catches missing model access and IAM problems before you save).
5. Click **Connect**.

Listing models needs `bedrock:ListFoundationModels` and `bedrock:ListInferenceProfiles`. If your credentials can't list models you can still type a model ID in **Custom model ID**.

**Test connection** also asks Bedrock which third-party models your account may use (`bedrock:GetFoundationModelAvailability`, which API keys can call). A model whose access agreement is missing is listed last and marked **Needs access** (or **Legacy, not used in 30 days** for a legacy model Bedrock no longer serves to accounts that have not used it recently); one with an open request shows **Access pending**. The list is kept for an hour per account and region under `~/.continuous/bedrock-catalog/`, so the prompt-cache tips and the config check that warns when a bare model ID needs an inference profile read it without further calls; **Test connection** always fetches a fresh list.

## Which authentication method should I use?

| Method | Best for | Fields |
| --- | --- | --- |
| [Bedrock API key](#bedrock-api-key) | Getting started quickly, personal use | `apiKey` |
| [AWS profile / SSO](#aws-profile-and-sso) | Work accounts, SSO or federated roles (recommended for teams) | `env.profile` |
| [Access keys](#access-keys) | CI, scripts, or temporary STS credentials | `env.accessKeyId`, `env.secretAccessKey`, `env.sessionToken` |
| [Environment / default chain](#environment-variables-and-the-default-credential-chain) | Existing AWS setup, EC2/ECS/Lambda roles | nothing |

If you configure nothing, Continuous uses the standard AWS credential chain, so an existing `aws configure` or `aws sso login` setup works without any Continuous-specific settings.

## Regions and endpoints

Pick the region where you have model access. Bedrock runtime is available in:

| Area | Regions |
| --- | --- |
| US | `us-east-1`, `us-east-2`, `us-west-2` |
| Canada | `ca-central-1` |
| Europe | `eu-west-1`, `eu-west-2`, `eu-west-3`, `eu-central-1`, `eu-central-2`, `eu-south-1`, `eu-south-2`, `eu-north-1` |
| Asia Pacific | `ap-northeast-1`, `ap-northeast-2`, `ap-northeast-3`, `ap-south-1`, `ap-south-2`, `ap-southeast-1`, `ap-southeast-2` |
| South America | `sa-east-1` |
| AWS GovCloud | `us-gov-east-1`, `us-gov-west-1` |

Availability changes over time, so use **Test connection** (or `aws bedrock list-foundation-models --region <region>`) as the source of truth. Not every model is in every region, and models must be enabled per account and region.

By default Continuous calls `https://bedrock-runtime.<region>.amazonaws.com`. Set `apiBase` to override that:

```yaml title="config.yaml"
models:
  - name: Claude via FIPS
    provider: bedrock
    model: us.anthropic.claude-sonnet-4-6
    apiBase: https://bedrock-runtime-fips.us-east-1.amazonaws.com
    env:
      region: us-east-1
```

- **FIPS endpoints** (`bedrock-runtime-fips.<region>.amazonaws.com`) exist in `us-east-1`, `us-east-2`, `us-west-2`, `ca-central-1`, `us-gov-east-1` and `us-gov-west-1`.
- **VPC / PrivateLink**: use the private DNS name of your `bedrock-runtime` interface endpoint as `apiBase`.
- **Proxies and gateways**: any HTTPS endpoint that accepts Bedrock Runtime requests works.

## Cross-region inference

Many newer models (for example Claude Sonnet 4) can only be invoked through an
*inference profile*, which has a regional prefix such as `us.`, `eu.`, `apac.`
or `global.`. If you see an error like "on-demand throughput isn't supported",
set `crossRegionInference` instead of editing the model ID by hand:

```yaml title="config.yaml"
models:
  - name: Claude Sonnet
    provider: bedrock
    model: anthropic.claude-sonnet-4-6
    env:
      region: eu-west-1
      crossRegionInference: auto # becomes eu.anthropic.claude-sonnet-4-6
```

| Value | Effect |
| --- | --- |
| `auto` | Chooses `us`, `us-gov`, `eu` or `apac` from `region` |
| `us`, `us-gov`, `eu`, `apac`, `jp`, `au`, `ca`, `global` | Uses that prefix explicitly |
| *(unset)* | Model ID is used exactly as written |

Model IDs that already start with a prefix (such as `us.anthropic...`) and
inference profile ARNs are never modified.

### Geographic or global?

| | Geographic (`us.`, `eu.`, `apac.`, ...) | Global (`global.`) |
| --- | --- | --- |
| Where requests are processed | Inside that geography | Any supported commercial region |
| Pricing | Standard | About 10% cheaper |
| Choose when | You have data-residency requirements | You want the best cost and availability |

Things to know:

- `auto` picks `us`, `us-gov`, `eu` or `apac` from your `region`. Some models are only offered through narrower profiles (`jp.`, `au.`, `ca.`) or only globally. For those, set the value explicitly, or choose the exact ID from **Test connection** in the UI.
- Profiles can route to different destination regions depending on the region you call from. For strict data residency, check the destinations with `aws bedrock get-inference-profile --region <region> --inference-profile-identifier <id>`.
- If you use Service Control Policies, they must allow Bedrock inference in every destination region of the profile (for global profiles, `"aws:RequestedRegion": "unspecified"`).
- Requests can be processed in regions you haven't enabled in your account; no opt-in is needed for cross-region inference.
- Application inference profiles (your own, for cost tracking) can be used by ID or ARN as the `model`.


## Advanced settings

All of these go under `env:` and are optional.

| Setting | Values | What it does |
| --- | --- | --- |
| `region` | AWS region | Region for requests and model listing |
| `profile` | profile name | Named profile from `~/.aws/config` (SSO supported) |
| `accessKeyId`, `secretAccessKey`, `sessionToken` | strings | Explicit credentials; add `sessionToken` for temporary ones |
| `crossRegionInference` | `auto`, `us`, `us-gov`, `eu`, `apac`, `jp`, `au`, `ca`, `global` | Adds the inference profile prefix to the model ID |
| `serviceTier` | `default`, `priority`, `flex`, `reserved` | Processing tier: `priority` is faster at a higher price, `flex` is cheaper but slower, `reserved` uses reserved capacity |
| `latency` | `standard`, `optimized` | Use latency-optimized inference on models that support it |
| `guardrailIdentifier`, `guardrailVersion` | ID or ARN, version | Apply a [Bedrock Guardrail](https://docs.aws.amazon.com/bedrock/latest/userguide/guardrails.html) to every request (version defaults to `DRAFT`) |

```yaml title="config.yaml"
models:
  - name: Claude (priority + guardrail)
    provider: bedrock
    model: anthropic.claude-sonnet-4-6
    env:
      region: us-east-1
      crossRegionInference: auto
      serviceTier: priority
      latency: optimized
      guardrailIdentifier: gr-abc123
      guardrailVersion: "1"
```

Whether a model supports a given tier or latency mode depends on the model and region; Bedrock returns a clear validation error if it doesn't. Extended thinking and prompt caching are controlled with `defaultCompletionOptions` (`reasoning`, `reasoningBudgetTokens`, `promptCaching`).

### What is sent per model family

Model families on Bedrock take different request fields, and the provider adjusts the request for each (measured live, November 2026):

- **Reasoning.** Claude gets Anthropic's `thinking` (adaptive with an effort on Claude 4.6 and later, a token budget before that). Nova 2 gets `reasoningConfig` with an effort of low, medium or high from `reasoningBudgetTokens` (about 1K, 4K or 16K), and `maxTokens` is left out at high because the model refuses it there; when the config says nothing about reasoning, Nova 2 runs at low, because without a `reasoningConfig` Nova 2 Lite writes its deliberation as plain text to the output budget and makes no tool call (measured 2026-11-08), and `reasoning: false` (or `reasoningEffort: off`) turns it off; Nova 2 returns its reasoning as the text `[REDACTED].` while billing the tokens, so it is shown as redacted thinking. Qwen3 and DeepSeek V3.2 get `reasoning_effort` (and `none` only when the config says `reasoning: false`). Kimi K3 and K3.1 get `reasoning_effort` on the Converse API only: with `reasoning: true` it is low, medium or high from `reasoningBudgetTokens` (up to 1K, up to 4K, above), with `reasoning: false` it is `none`, and when the config says nothing no field is sent and the model's own default applies (`max`, per AWS's model card). This rule follows the AWS model card and has not been tried against the live service. DeepSeek R1 always reasons and takes no field; Nova Pro, Lite, Micro and Premier, Llama and Mistral get nothing.
- **Sampling.** Claude refuses `temperature` and `topP` together, so only `temperature` is sent when both are set, and neither is sent while thinking is on. Other families take both.
- **Tools.** `toolChoice: auto` is always sent with tools (without it Llama writes the call as plain text). Tool use is on for Claude, every Nova, Mistral, Qwen3, GPT OSS, Llama 4 and DeepSeek V3; it stays off for DeepSeek R1 (which refuses tools) and Llama 3 (which refuses tools in streaming mode). Llama 4 refuses tools in streaming mode as well, and Qwen3 32B streams tool input with its opening fragment missing, so requests with tools to those models go through the non-streaming Converse call and the whole reply arrives at once; a model that answers "This model doesn't support tool use in streaming mode." is retried the same way and remembered for the process.
- **Model IDs.** With `crossRegionInference: auto`, a model that is only offered on demand (Qwen, DeepSeek V3.2, the newer Mistral models) refuses the geographic prefix with "The provided model identifier is invalid"; the request is retried once with the bare ID and the choice is remembered for the process.
- **Stop reasons.** A reply cut off at `maxTokens` arrives with `finish_reason: length`, and the CLI says so instead of treating it as complete.

## How to Enable Prompt Caching with Amazon Bedrock

Bedrock allows Claude models to cache tool payloads, system messages, and chat
messages between requests, and Amazon Nova 2 Lite, Nova Pro, Nova Lite and
Nova Micro to cache system messages and chat messages. Enable this behavior by
adding `promptCaching: true` under `defaultCompletionOptions` in your model
configuration.

```yaml title="config.yaml"
name: My Config
version: 0.0.1
schema: v1

models:
  - name: <MODEL_NAME>
    provider: bedrock
    model: <MODEL_ID>
    defaultCompletionOptions:
      promptCaching: true
```

Prompt caching is not supported in JSON configuration files, so use the YAML syntax above to enable it.

The cache lifetime is chosen from the chat toolbar, and 1 hour is available only for some Claude models; Nova takes 5 minutes only. See [Prompt Caching](../../deep-dives/prompt-caching.mdx).

## Broken streamed tool input

Some Qwen3 models on Bedrock stream a tool call whose input is cut or missing its opening `{"`. By default Continuous holds the call, and when the input does not parse it retries the request once through Converse. Set `CONTINUE_BEDROCK_REPAIR_STREAMED_TOOL_INPUT=1` in the environment that starts the editor or the CLI to repair such input instead, for model ids that contain `qwen.qwen3-` only. A repair is made only when it invents no value: a missing opening `{"` is added when every top-level key is one the tool declares, and brackets left open after a complete value (a string, `true`, `false`, `null` or a closer) are closed. Input that ends after a number, `{`, `,` or `:` is not repaired and is retried as before. It is off by default.

## When Bedrock refuses a request field

Some models refuse an optional field: Qwen, the newer Mistral models and gpt-oss refuse `stopSequences`, and GPT, Grok and some Nova requests refuse a `cachePoint`. Continuous knows the documented cases up front and never sends those fields to such models. If a model still refuses one of these two fields, the request is sent once more without it, the model is remembered for the rest of the run, and the `cn` command line says so once and lists it in its exit summary, with the config change that makes it permanent: `defaultCompletionOptions.promptCaching: false` for cache points, or removing `stop` from the model's options. Fields that change the answer, such as tools or the system prompt, are never dropped this way. Nothing is remembered across runs; put the setting in `config.yaml` to make it stick.

## Authentication

### Bedrock API key

[Bedrock API keys](https://docs.aws.amazon.com/bedrock/latest/userguide/api-keys.html) are the simplest option. Create a long-term key in the Bedrock console (**API keys**) and set it with `apiKey`:

```yaml title="config.yaml"
models:
  - name: Claude Sonnet
    provider: bedrock
    model: anthropic.claude-sonnet-4-6
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
    env:
      region: us-east-1
      crossRegionInference: auto
    roles:
      - chat
```

You can also export the key as `AWS_BEARER_TOKEN_BEDROCK` and omit `apiKey`. The
variable is ignored if you set `profile` or access keys explicitly.

### AWS profile and SSO

Use this for work accounts. Continuous never sees your keys; it reads the profile
from `~/.aws/config`.

```bash
aws configure sso --profile my-bedrock   # one-time setup
aws sso login --profile my-bedrock       # whenever the session expires
```

```yaml title="config.yaml"
models:
  - name: Claude Sonnet
    provider: bedrock
    model: anthropic.claude-sonnet-4-6
    env:
      region: us-east-1
      profile: my-bedrock
      crossRegionInference: auto
    roles:
      - chat
```

If you set `profile` and it can't be loaded, Continuous reports an error (with an
`aws sso login` hint when the SSO session has expired) rather than silently
using a different profile.

### Environment variables and the default credential chain

With no `apiKey`, `profile` or keys configured, Continuous first tries a profile
named `bedrock` (for backwards compatibility) and then the standard AWS chain:
`AWS_ACCESS_KEY_ID` / `AWS_SECRET_ACCESS_KEY` / `AWS_SESSION_TOKEN`, the
`[default]` profile, SSO, and container or instance roles.

### Required permissions

Chat needs `bedrock:InvokeModel` and `bedrock:InvokeModelWithResponseStream`.
For inference profiles, grant them on the profile ARN as well as the underlying
foundation models in each region. Bedrock API keys additionally need
`bedrock:CallWithBearerToken`. Listing models in the UI needs
`bedrock:ListFoundationModels` and `bedrock:ListInferenceProfiles`. Bedrock API keys
only work with Bedrock and Bedrock Runtime actions, which covers everything Continuous
does.

### Optional quota check

AWS can apply a tokens-per-minute quota of **0** to a model for an account, even when model access shows as granted; every request to that model is then refused with "not available for this account". If the credentials can read Service Quotas, Continuous names such a model **before** the first request: on **Test connection** (the selected model gets a warning with a link to the Service Quotas console) and when you select a Bedrock model (one notification per model and region):

> us.anthropic.claude-opus-5-5 has a 0 tokens-per-minute quota in us-east-1 for this account; request an increase in Service Quotas

The permission is **optional**. Add it to the IAM identity Continuous uses if you want the check:

```json title="IAM policy"
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "ContinuousBedrockQuotaCheck",
      "Effect": "Allow",
      "Action": "servicequotas:ListServiceQuotas",
      "Resource": "*"
    }
  ]
}
```

What happens without it, or when the check cannot run:

- **No permission** (`AccessDeniedException`): Test connection still succeeds and shows one quiet line, "Quota check skipped: this profile lacks servicequotas:ListServiceQuotas". No error and no notification. The answer is remembered for this profile and region for a day, or until the credentials change, so Service Quotas is not asked on every connection. A model with a 0 quota is then reported after its first refused request, with the same advice.
- **Bedrock API key**: Service Quotas needs AWS credentials, so the check is skipped (one quiet line on Test connection).
- **Throttling, a network error, a region without Service Quotas, or no answer within 5 seconds**: skipped with one quiet line and tried again later (15 minutes after throttling, an hour after a timeout or network error, a day for a region without the service). Test connection, the model list and chat never wait longer than that for it.

The check reads `ListServiceQuotas` for service code `bedrock` in the configured region, with the same credentials, profile, proxy and certificate settings as the Bedrock requests, and matches the per-minute on-demand, cross-region and global quotas to the model by name. The result (quota names and values, no account id or key) is kept in `model-catalog/` in the global folder for `modelCatalogRefreshHours`. It follows the [model information updates](/reference#modelcatalog) setting: **Automatic** checks on Test connection, on selecting a model and in the background for the selected model; **Only when I ask** checks on Test connection only; **Off** never checks.

### Prices from the AWS Price List

Cost estimates for Bedrock models use the AWS Price List for the selected model's region when it is available, ahead of the prices built into Continuous, and the cost breakdown names it ("AWS Price List, us-east-1 in-region, downloaded 2026-11-13"). It includes the flex and priority tiers and the global cross-region rates where AWS lists them, so a request Bedrock served at the flex tier is priced at the flex rate. Models the Price List does not cover (Claude is priced from Anthropic's list with the regional premium) keep the built-in prices.

The Price List is a public file: one `GET https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonBedrock/current/<region>/index.json` with no AWS credentials and no IAM permission. It is large, so it is read as a stream and only the per-token prices are kept, in `model-catalog/bedrock-prices-<region>.json`. It is requested only when a Bedrock model is configured, and follows the model information updates setting: **Automatic** downloads it when you select a Bedrock model and in the background when the copy is older than `modelCatalogRefreshHours`; **Only when I ask** downloads it on Bedrock Test connection; **Off** never downloads it and ignores a copy kept from before. A failed download leaves the previous copy, or the built-in prices, in use.

## Corporate proxies and TLS inspection

Bedrock requests use the same `requestOptions` as every other model, so they work behind an HTTP(S) proxy and a TLS-inspecting firewall without extra tooling:

```yaml title="config.yaml"
models:
  - name: Claude Sonnet
    provider: bedrock
    model: us.anthropic.claude-sonnet-4-6
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
    env:
      region: us-east-1
    requestOptions:
      useSystemCa: true              # trust the OS certificate store (default on Windows and macOS)
      # caBundlePath: /path/to/corp-root.pem   # or point at the root certificate directly
      # proxy: http://proxy.corp:3128
      # noProxy: [".internal.example.com"]
```

| Setting | What it does |
| --- | --- |
| `useSystemCa` | Also trusts the operating system's certificate store. On by default for Windows and macOS, off on Linux. Needs Node.js 22.15 or newer. |
| `caBundlePath` | Trusts the certificates in a PEM file (or a list of files). `NODE_EXTRA_CA_CERTS` is honoured too. |
| `proxy` / `noProxy` | Uses the given proxy; falls back to `HTTPS_PROXY` / `NO_PROXY` from the environment. Proxy credentials go in the URL (`http://user:pass@host:3128`). |
| `verifySsl: false` | Skips certificate verification. Only for debugging. |
| `clientCertificate` | Presents a client certificate (`cert`, `key`, optional `passphrase`). |

These apply to model requests, model listing and **Test connection**.

When none of these are needed Continuous leaves the AWS SDK's own networking alone. When one is, it switches the SDK to HTTP/1.1 through Continuous's proxy-aware agent; streaming works the same.

If the certificate isn't trusted you'll see an error such as "unable to get local issuer certificate", followed by a hint pointing at `useSystemCa` and `caBundlePath`.

## Troubleshooting

| Error | Fix |
| --- | --- |
| "on-demand throughput isn't supported" | Set `crossRegionInference: auto` |
| "You don't have access to the model" | Enable the model under **Model access** in the Bedrock console, in the same region |
| "marked by provider as Legacy and you have not been actively using the model" | Bedrock no longer serves this legacy model to your account; pick a current model (**Test connection** marks the ones that need access) |
| "Please make sure your API Key is valid" | A short-term API key works only in the region it was generated for: make `region` match it, or create a key for this region. A long-term key may have expired |
| AWS SSO session expired | Run `aws sso login --profile <name>` |
| "Could not load credentials" | Configure one of the methods above |
| "not available for this account" | The account's tokens-per-minute quota for the model is probably 0 in this region: check Service Quotas > Amazon Bedrock and request an increase ([quota check](#optional-quota-check)) |
| "Quota check skipped: this profile lacks servicequotas:ListServiceQuotas" | Informational. Add the [optional permission](#optional-quota-check) to see 0 quotas before the first request |
| "unable to get local issuer certificate" / "self-signed certificate" | Your network inspects TLS. Set `requestOptions.useSystemCa: true` or `caBundlePath` ([details](#corporate-proxies-and-tls-inspection)) |
| 407 Proxy Authentication Required | Put credentials in the proxy URL, e.g. `requestOptions.proxy: http://user:pass@proxy:3128` |
| Anthropic "use case details" prompt | Open the Bedrock Playground, choose an Anthropic model and submit the form |

## Bedrock Mantle (OpenAI-compatible endpoint)

Bedrock also serves models through an OpenAI-compatible API at `bedrock-mantle.<region>.api.aws`, called **Mantle**. Use the `bedrock-mantle` provider with a [Bedrock API key](#bedrock-api-key) when a model you want (for example GPT OSS, Qwen or Kimi) is available there, or to use features that only exist on Mantle.

```yaml title="config.yaml"
models:
  - name: GPT OSS 120B
    provider: bedrock-mantle
    model: openai.gpt-oss-120b
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
    env:
      region: us-east-1
    roles:
      - chat
```

You can also add it from the UI: **Add Chat model**, then **Amazon Bedrock (Mantle)**, then **Test connection** to list the models your key can use. The **Model** list then shows them with readable names; embedding and speech models are left out. You usually do not need this entry: the plain **Amazon Bedrock** entry also lists Mantle-only models when you use an API key.

### Models that need approval

Some models are gated: your account can see the endpoint but not the model, or a policy denies it. The error text tells you which:

- **"explicit deny"**: an IAM identity policy, permissions boundary or service control policy blocks it. Enabling the model in the console will not help; ask your AWS administrator.
- **Not in the Test connection list**: your key is not entitled to it in that region. Restricted models (for example security-focused or limited-preview models) can also need separate approval from the model provider, so check the provider's access program as well as AWS.
- **Present in the list but the request is rejected**: check the path prefix (`mantlePathPrefix`) and the token parameter (`maxTokensParam`) below.

If a model you expect is missing from the list, type its ID into **Custom model ID (optional)**; the model card lists the ID and path prefix.

To use every model your key can access without listing them by hand, set `model: AUTODETECT`; Continuous fills in the list from `GET /v1/models`.

### Mantle vs standard Bedrock

| | `bedrock` (Converse API) | `bedrock-mantle` |
| --- | --- | --- |
| Authentication | API key, profile / SSO, access keys | Bedrock API key (or `AWS_BEARER_TOKEN_BEDROCK`) |
| Cross-region inference profiles | Yes | No |
| Guardrails, service tier, latency mode | Yes | No |
| Regions | 22 | 15 (see below) |
| IAM permission | `bedrock:InvokeModel*` | `bedrock-mantle:CreateInference` |

Per-token prices are the same on both endpoints. AWS recommends the standard endpoint for new applications and Mantle when you need a model or capability only available there. Which models each endpoint serves is listed in AWS's [Endpoint availability](https://docs.aws.amazon.com/bedrock/latest/userguide/models-endpoint-availability.html) table: most models are on both, some are on only one (for example, at the time of writing, Claude Mythos 5 and the Gemma 4 models are Mantle-only, while Kimi K3 and Claude Opus 4.6 are standard-endpoint-only). That table changes often, so use **Test connection**, which asks the endpoints directly.

**Mantle regions:** `us-east-1`, `us-east-2`, `us-west-2`, `eu-central-1`, `eu-north-1`, `eu-south-1`, `eu-west-1`, `eu-west-2`, `ap-northeast-1`, `ap-south-1`, `ap-southeast-2`, `ap-southeast-3`, `sa-east-1`, `us-gov-east-1`, `us-gov-west-1`. Regions such as `eu-west-3` or `ap-southeast-1` have no Mantle endpoint.

### Per-model quirks (handled automatically)

- **Path prefix.** Most models are served under `/v1`, some under `/openai/v1`. If a request is rejected with "isn't supported on this route", Continuous retries on the other prefix and remembers it. To set it yourself, use `mantlePathPrefix` (the model card lists it under Programmatic Access).
- **Token limit parameter.** Some models reject `max_tokens`. Continuous switches to `max_completion_tokens` when it sees that error. To force it, set `maxTokensParam: max_completion_tokens` (or `max_tokens`).

```yaml title="config.yaml"
models:
  - name: Custom route
    provider: bedrock-mantle
    model: openai.some-model
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
    env:
      region: us-east-1
      mantlePathPrefix: /openai/v1
      maxTokensParam: max_completion_tokens
```

### Using the OpenAI-compatible API on the standard endpoint

`bedrock-runtime` also serves the OpenAI Chat Completions and Responses APIs at `https://bedrock-runtime.<region>.amazonaws.com/openai/v1`, with Guardrails and cross-region inference profiles (for example `global.openai.gpt-5.6-sol`). Point the same provider at it with `apiBase`:

```yaml title="config.yaml"
models:
  - name: GPT via bedrock-runtime
    provider: bedrock-mantle
    model: global.openai.gpt-5.6-sol
    apiBase: https://bedrock-runtime.us-east-1.amazonaws.com/openai/v1/
    apiKey: ${{ secrets.BEDROCK_API_KEY }}
```

That endpoint has no `GET /models`, so list models with **Test connection** on the standard Bedrock provider instead. When `apiBase` is set, Continuous does not auto-detect the path prefix.

## How to Configure Custom Imported Models with Amazon Bedrock

To setup Bedrock using custom imported models, add the following to your config file:

<Tabs>
  <Tab title="YAML">
  ```yaml title="config.yaml"
  name: My Config
  version: 0.0.1
  schema: v1

  models:
    - name: <MODEL_NAME>
      provider: bedrockimport
      model: <MODEL_ID>
      env:
        region: us-west-2
        profile: bedrock
        modelArn: arn:aws:bedrock:us-west-2:XXXXX:imported-model/XXXXXX
  ```
  </Tab>
  <Tab title="JSON (Deprecated)">
  ```json title="config.json"
  {
    "models": [
      {
        "title": "<MODEL_NAME>",
        "provider": "bedrockimport",
        "model": "<MODEL_ID>",
        "modelArn": "arn:aws:bedrock:us-west-2:XXXXX:imported-model/XXXXXX", 
        "region": "us-west-2",
        "profile": "bedrock"
      }
    ]
  }
  ```
  </Tab>
</Tabs>

Authentication will be through temporary or long-term credentials in
~/.aws/credentials under a configured profile (e.g. "bedrock").

```title="~/.aws/credentials
[bedrock]
aws_access_key_id = abcdefg
aws_secret_access_key = hijklmno
aws_session_token = pqrstuvwxyz # Optional: means short term creds.
```
