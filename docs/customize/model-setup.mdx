title: "Set Up Providers and Models"
---

Open the setup flow with **Add a model**: the **+** on **Settings > Models**, **Add a model...** in the model picker, the notice the chat shows when no model is selected, or the first-run onboarding card. It also opens from **Connections** on **Settings > Models** (**Add provider**, or an action on an existing connection row), from the model picker's **Manage models...**, and from the command palette:

- VS Code: `Continuous: Manage Models and Providers`

**Add a model** first asks what you have:

- **An API key**: choose the provider, then paste the key.
- **A server on this computer**: the servers that answer on the usual local ports are listed with their address and model count, for example "Found: Ollama at 127.0.0.1:11434, 2 models". Choosing one goes straight to its models. Only the loopback addresses in [Local servers](/customize/model-providers/more/local-servers) are asked, each for at most 1.5 seconds; after 5 seconds the line reads "None found".
- **A server on my network**: enter the address of an OpenAI-compatible server on another machine.
- **Nothing yet**: install Ollama and download one model, or open a provider's page to make a key. Nothing is downloaded or opened until you press its button.

Every answer then takes the same four steps, and nothing is written until you confirm the last one.

1. **Connection.** The provider, the API key or the server address, and where the key is kept. **More** holds what is rarely needed: the API base, the name the key is saved under, the proxy, certificates, and the request and connect timeouts. Each field there says what applies when it is not set (for example "Not set: 7,200 s for the whole reply"), and a field left alone is not written.
2. **Models.** Tick the models to use. Each row gives the model's context window, its price per million input and output tokens, and whether it takes tools; what is not known reads "not published", "no price known" or "not reported". Models already in your `config.yaml` start ticked. The list can be refreshed from the provider with the entered credentials.
3. **Use for.** Chat, Edit and Apply start ticked. Autocomplete is ticked only for a model the catalog recommends for it. Each line says what the role uses now and what it will use, for example "Chat: currently Claude Sonnet → will be Qwen 3": the first model you ticked becomes the selected model of each ticked role. With Chat, Edit and Apply ticked no `roles` are written; any other choice is written with the model. The step is skipped when no model is added.
4. **Review.** Lists the models to add and remove, the roles, what **More** set, and where the key goes. Removing models needs a separate confirmation, and removed models are also taken out of the `modeModels` lists.

## Connections on the Models tab

**Settings > Models** lists each provider connection in the selected config under **Connections**, below the models in use, one row each: the provider and its icon, the account or endpoint and region, how it signs in (for example "Key CONTINUOUS_ANTHROPIC_API_KEY in secure storage", "Key ... in ~/.continuous/.env", "AWS SSO profile work" or "AWS default credentials"), and how many models are enabled. Key values are never shown. For an AWS profile, the row says how it signs in (SSO, `credential_process`, an assumed role, a web identity token, or access keys in `~/.aws/config` or `~/.aws/credentials`), read from the names of the keys in the profile's section of `~/.aws/config` (or `AWS_CONFIG_FILE`); no value is read, and `~/.aws/credentials` is not opened. A key that is in neither secure storage nor `~/.continuous/.env` is marked, since it has to come from an environment variable. Below the connections are the [provider accounts](/customize/providers) of `~/.continuous/providers.yaml`.

Open it from the Settings sidebar (**Models**), from **Providers...** in the model picker, or with `Continuous: Open Providers` in VS Code. Providers was a tab of its own before; a link to `/config?tab=providers` opens Models at **Connections**.

Each row has:

- **Manage models**: the setup flow at the model checklist for that connection.
- **Edit connection**: the setup flow at the credentials step, to change the key or the endpoint.
- **Test connection**: opens the settings of the connection's first model at Connection, where **Test connection** runs, as `Continuous: Test Connection of the Chat Model` does for the chat model.
- **Remove**: after a confirmation that names the models, takes the connection's models out of the selected config and out of the `modeModels` lists. Stored keys are not deleted, and for a connection that uses an account, the account in `providers.yaml` and its catalog models stay; delete the account under **Provider accounts**.

With no connection yet, the page shows **Add a provider**.

## Test connection

In the setup flow the test runs by itself, and only lists the models (`GET <api base>/models`, which spends no tokens): at once when a server or a usual address is picked, 300 ms after a key or an address is pasted, and one second after typing stops when the key has 20 characters or more with no space (for a server, when the address is a full `http` or `https` address). It never runs on a keystroke, the same provider, address and key are tested by themselves only once, a change drops a test that is waiting or running, and **Stop** drops one that is running. Its line reads, for example, "Connected. 14 models. Tools: yes." **Test again** repeats it, and **Check tool calls** sends the one request described below, which a provider bills. A server on this computer or network that does not answer is described in words: which address, what happened, and what to check.

For OpenAI, Ollama, llama.cpp, LM Studio, llamafile, vLLM, text-gen-webui, Msty, OpenRouter, DeepSeek, Groq, Together, Mistral and any provider with an API base, the model's settings (Configure, Connection) have **Test connection**. It lists the models the endpoint serves (`GET <api base>/models`), asks Ollama (`/api/show`) or llama.cpp (`/props`) whether the server parses this model's tool calls itself, and, when a model is chosen, sends one request offering a made-up tool and says how the model answered: `Tool use: ...` with the result, or `Tool use: could not tell (...)`. The tool is never run, the key is sent only as a bearer header and is never shown, and a failure shows `Could not connect` with the endpoint's error. Amazon Bedrock has its own form; see [Amazon Bedrock](/customize/model-providers/top-level/bedrock).

The same check runs from a terminal:

```bash
continuous test-connection --provider ollama --model qwen3-coder
continuous test-connection --provider openai --api-key-env OPENAI_API_KEY --model gpt-4.1
```

`--provider` is required. `--api-base <url>` overrides the provider's default endpoint (a provider with no default needs it), `--api-key-env <name>` names the environment variable that holds the key, `--model <id>` adds the tool-call probe, and `--json` prints the result as JSON. Exit code 0 means connected, 1 means the connection failed and 2 means a missing `--provider` or an unset key variable.

One provider connection (a provider plus its API base, region or profile) has one key, and every model you tick for it refers to that key. Editing the API base, region or profile of an existing connection changes that connection in place: its models keep their names and settings. If another connection already uses the new endpoint, the save is refused.

Saving edits the selected config's YAML file and keeps your comments and key order. It is unavailable when the selected config is not a local YAML file (for example, if you only have a `config.json`). To share one key between several configs, use [provider accounts](/customize/providers) instead.

## Where API keys are stored

Choose one per connection under "Keep the key in". `config.yaml` never contains the key unless you choose the last option.

| Option | What is written | Notes |
| :-- | :-- | :-- |
| Secure storage | The key goes to the IDE's secret storage. `config.yaml` gets `apiKey: ${{ secrets.CONTINUOUS_<PROVIDER>_API_KEY }}`. | Default when the IDE can store and read back a test value: VS Code secret storage. Not readable by the CLI or other tools. |
| `~/.continuous/.env` file | The key is added to `~/.continuous/.env` (owner-only permissions). `config.yaml` gets the same reference. | Plaintext. Works with the CLI and anything else that reads `.env`. Default when secure storage is unavailable. |
| Environment variable | Nothing is stored. `config.yaml` refers to the name you type. | For keys injected by something else. IDE extensions only see variables present when the IDE was launched. |
| Inside `config.yaml` | The key is written into each model entry. | Not recommended: the file is often synced or committed. |

Your last choice is remembered. Existing configs are not changed.

### Lookup order

`${{ secrets.NAME }}` is resolved from the first of these that has a value:

1. The IDE's secure storage
2. `~/.continuous/.env`
3. `<workspace>/.continuous/.env`
4. `<workspace>/.env`
5. Process environment variables

Because secure storage is read first, a key saved there wins over an older copy in `~/.continuous/.env`. When you save a key to secure storage and `~/.continuous/.env` has the same name, the flow asks whether to remove that line. It never deletes it without asking, and only does so once the key is in secure storage.

### Move an existing key to secure storage

On **Settings > Models**, under **Connections**, a connection whose key is only in `~/.continuous/.env` shows **Move key to secure storage**. After you confirm, Continuous copies the value into secure storage, checks that it reads back, and then removes that line from `~/.continuous/.env`. `config.yaml` is unchanged, since it already refers to the secret by name. The key value stays in the extension host and is not sent to the chat panel. If the key is in both places, the row offers **Remove .env copy** instead.

### A synced config on a new machine

Secure storage is per machine. If `config.yaml` refers to a secret that has no value on this machine, the model shows as "Key not set", and the warning icon above the chat input offers **Enter key**, which opens the flow at the credentials step.
